# ADR-0018: The sandbox notice lives in the agent's home, never in a repo

- Status: **Accepted**
- Date: 2026-09-15
- Deciders: nranthony (owner, via the sandbox tool's ADR-0015 of 2026-09-14) + agent
- Distilled from: **macolima ADR-0015** (the sandbox tool's repo, Accepted 2026-09-14)
  and the handoff it sent here,
  `macolima/work/0011-sandbox-notice-global-homes/handoff-depot.md`, delivered to
  `depot/inbox/` on 2026-09-14. The adoption is tracked in
  [work/0023](../../work/0023-sandbox-notice-leaves-the-repo/notes.md).

## Context

The blueprint's "Environment notice" section has, since the sandboxed-execution tier was
added, told a repo edited inside a restricted sandbox to carry a machine-managed block at
the very top of its root `AGENTS.md`: `BEGIN/END sandbox-notice (managed by <tool>)`,
generated by the sandbox tool, never hand-edited. The reasoning was sound and still is —
an agent that meets a deny-list without warning burns turns retrying and hunting for
bypasses, so the enforcement needs a matching piece of advice. What was wrong was *where
the advice was kept*.

**A per-repo block is unfixable from inside the repo.** The ownership rule — humans and
agents never edit inside the markers — is what makes a generated block trustworthy, and
it is the same rule that leaves a stale block with no route to repair. The repo's agent
may not touch it; the sandbox tool only rewrites it on a converge that reaches that
checkout. Between those two, nothing happens. On the Mac on 2026-09-14, eight repos
carried a block, **none** had been refreshed since it was placed, and all of them
contradicted the repo around them.

**One slot, two sandboxes.** A repo seen by both sandboxes has one place for the block
and two generators writing different markers into it. Each recognised only its own
spelling, so the second did not replace the first — it **stacked** a second block on top
of it. Measured in macolima, not predicted.

**The agent's home is the natural slot.** Both sandboxes already write per-agent
configuration on every `up`/`converge`, and a notice put there is in context before any
repo is opened, covers every checkout on the machine, and refreshes in one place. The
block's markers also became sandbox-neutral in the same change, so a future migration is
a rename rather than a second block.

This record adopts that decision on the blueprint side. The sandbox halves — the notice
text, the two write targets, the scanner flag and the strip — are macolima's and already
landed there; windows-ai-sandbox adopts them by replay.

## Decision

**1. The sandbox briefs agents from each agent's global home.** It writes its notice into
`~/.claude/CLAUDE.md` (Claude Code) and `~/.gemini/config/rules/sandbox-notice.md` (agy)
on every `up`/`converge`. That is the sandbox tool's job, as the block's content always
was.

**2. A repo carries no block, and the blueprint no longer asks for one.** Sandboxed
execution stops being an opt-in tier with a file attached: a repo edited in a sandbox and
a repo that never sees one carry the same thing, nothing. A repo's `AGENTS.md` is the
repo's own text, top to bottom. `templates/AGENTS.md` seeds no block and its comment now
says so.

**3. A block found inside a repo is stale by definition, and is reported, not fixed.**
It predates this decision and nothing refreshes it. The fix is removal by the sandbox's
owner, with the owner's own tooling — in macolima, `workspace-scan.py` reports it as
`NOTICE-IN-REPO` and `sync-agent-notice.sh --strip` removes it. An agent that meets one
says where it is and stops there.

**4. The read-only rule survives unchanged, and is now the whole rule.** Never editing
inside the markers is still not never looking inside them: resolve every path and named
script the block cites, exactly as for the rest of `AGENTS.md`, and report a dead
reference along with the block. Editing inside the markers stays forbidden — including
to "fix" a stale block, which is the failure this record exists for. Adding a block is
forbidden outright, in any form: empty, speculative, or hand-written for a sandbox with
no managing tool.

**5. The block shape stays in the blueprint as something to recognise.** The neutral
spelling is:

```
<!-- BEGIN sandbox-notice (managed by the sandbox — do not edit here) -->
…
<!-- END sandbox-notice -->
```

The two legacy spellings, `managed by macolima …` and `managed by windows-ai-sandbox …`,
are recognised by the sync scripts **for migration only**. Read all three as the same
block.

**6. The content rules keep their place, addressed to the generator.** State what fails
framed as "don't retry", reframe every denial as a human step, state what works, and name
the ask rather than the host-side mechanism. They are instructions for whoever writes a
notice — the sandbox tool — not for a repo. The fourth gains a consequence: a notice
written into an agent's home has no repo around it, so a repo-relative path there
resolves nowhere and must not appear.

## Consequences

- **The blueprint keeps a section about a file it no longer tells anyone to write.** That
  is deliberate. Blocks exist in the field, and an agent that meets one with no guidance
  will either trust it or repair it — both wrong. The section now teaches recognition and
  reporting, and keeps the content rules for the tool that generates one.
- **`/myconv:apply-conventions` reports a block as a gap** instead of verifying it as a
  read-only fixture. Both sites that assumed a block was present — step 1 of the skill
  and phase 2 of the brownfield procedure — now treat finding one as a finding.
- **This ships as myconv 0.10.0**, and reaches a sandbox only when the owner re-vendors
  the plugin. Until then a container's seeded copy still instructs the old shape.
- **Repos already carrying a block are not fixed by this release.** The sandbox owner
  strips those. The depot's own two members did it by hand on 2026-09-14 — myclickup
  `55c7999`, paperbridge `ccb1b65` — which the handoff's §3 had already assumed was
  never needed.
- **The lean core is unchanged.** Removing the sandboxed-execution tier removes an
  opt-in, so no repo that followed the blueprint loses anything it depended on.
- **This record reopens if a sandbox appears that cannot write into an agent's home.**
  The per-repo block would then be the only slot again, and its two failures would have
  to be solved rather than avoided.

## Alternatives considered

- **Keep the per-repo block and have the sandbox refresh it on every converge.**
  Rejected: it needs write access into every checkout on every converge, which is a much
  larger standing permission than writing one file in the agent's own home — and it does
  not touch the stacking failure at all, since the slot is still shared by two
  generators.
- **Let a repo's agent edit inside the markers when the block is stale.** Rejected: the
  no-edit rule is exactly what makes a generated block worth trusting. An edited block
  still claims to be generated, and the next converge overwrites the repair anyway.
- **Teach each sandbox to recognise the other's markers, so the second replaces the
  first.** Rejected as a patch on the wrong layer: it fixes stacking and leaves the
  unfixable-from-inside failure, and it makes every future sandbox a change to every
  existing one.
- **Drop the section from the blueprint entirely.** Rejected: an agent that meets a block
  in an old repo needs to know it is stale, and the content rules still have an owner.
- **Template the notice's content here.** Rejected in the original section and rejected
  again: a copied deny-list drifts from the real sandbox config the first time the
  sandbox is tweaked, and a stale notice is worse than none. That reasoning is now the
  argument for the whole block living with its generator.
