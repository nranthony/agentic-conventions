# Proposal: `validation/` — a home for measured-behaviour evidence

- Status: Accepted → ADR-0009
- Author: nranthony + agent
- Date: 2026-08-11 (decisions folded in 2026-08-12)
- Origin: a signal-processing repo needed somewhere to put a committed record of measured
  detector accuracy that a CI gate reads by path. Neither `docs/`, `tests/`, nor `work/`
  was right, which is the tell that a category is missing.

## Summary

Add an opt-in `validation/` tier to the blueprint: a committed, corpus-organised home for
**evidence of measured system behaviour against ground truth**, split into a hand-edited
`expected.json` (what the gate enforces) and a regenerated `measured.json` + `measured.md`
(what the last run actually produced).

Scoped deliberately to ground-truth accuracy evidence. Performance benchmarks, golden-output
snapshots and external scan reports are **out** — see *Scope boundary*.

Enforcement is deliberately **not** part of this. The tier ships as convention: fixed names,
two stated rules, and an index. What that does and does not buy is stated plainly below
rather than overclaimed.

## Motivation

### The gap is real, not a filing preference

The repo that raised this has four provenance tiers and the artifact fits none:

| Tier | What it holds | Why this artifact doesn't fit |
|---|---|---|
| `docs/` | prose canon | a machine-read JSON blob is not prose |
| `tests/` | executable checks | this is an *input* to a check, not a check |
| `docs/adr/` | decisions and their reasoning | a measurement is not a decision |
| `work/` | in-flight items | **`work/` archives on completion; this has a live CI consumer.** Archiving a build dependency is a contradiction |

That last row is the decisive one. `work/`'s exit rule — distil, then archive — is load-bearing
(ADR-0006), and an artifact that a gate reads by path can never satisfy it.

The missing category is **evidence**: a dated record of how the system behaved when measured,
committed on purpose, superseded rather than edited. It is closest in spirit to an ADR — both
are records of a moment — but ADRs record *what we decided*, and this records
*what we measured*.

### It multiplies

One corpus is a file; four is a tree. The originating repo already has one corpus pinned, a
second with numbers worth pinning, a third arriving with its next work item, and any detector
version bump needs a before/after pair. A convention adopted at one file costs nothing; adopted
at ten it is a migration.

### What the split makes visible — and what it does not

If one file is both the record and the gate's authority, then **regenerating it moves the
goalposts**, and the diff looks like routine churn. A run that quietly drops two points of
sensitivity produces a green build and a plausible-looking commit.

Splitting authority from record removes that path: the gate reads `expected.json`, so
regenerating `measured.*` cannot change what passes. What remains possible is a hand-edit to
`expected.json` — and that is the point. It becomes **a one-line diff to a named file with a
required justification beside it**, rather than a number buried in a regenerated blob.

**The claim is legibility, not prevention.** Nothing here stops a threshold being loosened.
It stops it being loosened *invisibly*. Enforcement — a `CODEOWNERS` entry, or a check that
flags a hand-edited record — is deferred, with its trigger recorded in the ADR.

## Proposal

### 1. The directory

```
validation/
├── README.md                # index: what evidence exists, which gate reads what, how to regenerate
└── <corpus>/                # one directory per corpus or dataset
    ├── expected.json        # hand-edited. The gate's authority. Never machine-written.
    ├── measured.json        # regenerated. The record of the last run. Never hand-edited.
    └── measured.md          # regenerated by the same command. The human-readable table.
```

Organised **by corpus**, not by metric or by date — a corpus is the unit a reader asks about
("how do we do on NSTDB?"), and the unit that changes independently. Where one corpus carries
several independent harnesses, nest one level: `<corpus>/<harness>/expected.json`.

### 2. The filenames are fixed, and generic on purpose

`expected` / `measured` are the same in every repo. A reader entering an unfamiliar repo
should be able to tell which file is authority and which is record without opening either.

A repo-specific name fails that twice over. The originating repo's `beat_truth.json` says
nothing about whether it is the thing being enforced or the thing being recorded — and
"truth" conventionally names the *reference labels*, not a measurement of performance against
them, so the name points at the wrong artifact entirely. Adopting the tier renames it.

Two rules follow directly from the names, and both are stated at the top of every
`validation/README.md`:

- **Nothing regenerates `expected.json`.** A regeneration script that writes it is a bug.
- **Nobody hand-edits `measured.*`.** A hand-edit there is falsifying a record.

Both files are JSON, and **every threshold carries a required `why`** — a number with no
stated reason is exactly what gets loosened silently later:

```json
{
  "sensitivity": {
    "min": 0.995,
    "why": "floor agreed in ADR-00XX; record 207's flutter run is the binding case"
  }
}
```

`expected.json` stays small: tolerances and thresholds, never a mirror of the measurements.

> **Reversed during review.** This was TOML first, chosen for comment syntax. The criterion
> that flipped it was *what is easiest for agents downstream*. TOML is free to read only in
> Python 3.11+ (`tomllib`); everywhere else — Node, Go, shell, a `jq` one-liner, a raw Actions
> step — it needs a parser package, and under this project's standing dependency rule that is
> a **stop-and-ask**, not a detail. An agent working in one of those repos would have to
> interrupt a human to read a five-line thresholds file. JSON needs no dependency anywhere,
> and makes both files one format so a gate needs one parser rather than two.
>
> The `why` **field** then turns out to beat the comment it replaced: it can be required, it
> can be validated, and — the property worth the trade on its own — a gate can quote it in the
> failure message. `sensitivity 0.993 < 0.995 (floor agreed in ADR-00XX; record 207's flutter
> run is the binding case)` is a better artifact than a silent failure beside a comment nobody
> reads. The cost accepted: JSON has no comment syntax, so someone will eventually try `//`
> and break the file. The required `why` is the sanctioned place and the template says so.

### 3. Every record carries its provenance

A number is meaningless without what produced it. `measured.json` opens with:

```json
{
  "provenance": {
    "generated": "2026-08-11",
    "commit": "b472aef",
    "command": "python scripts/beat_report.py --write",
    "corpus": "MIT-BIH Arrhythmia Database v1.0.0",
    "corpus_digest": "sha256:…"
  },
  "records": { }
}
```

`measured.md` repeats it as a header, so the human artifact is self-dating.

`corpus` and `command` are required. `command` earns that because the end-state for an
un-regenerable record is folklore — nobody remembers how to refresh it, so nobody does, and it
silently degrades from evidence into a claim.

`corpus_digest` is strongly recommended and **may lag** where the corpus ships a stable
published version identifier. Its job is narrower than it first appears: the version string
already distinguishes a genuine data change from a regression, so the digest is guarding
against local corruption and partial downloads. Real, but not urgent — a repo may adopt the
tier with the version string alone and add the digest the first time a result cannot be
explained. Where a corpus has no authoritative version identifier, the digest is the only
thing standing between an apparent regression and an unnoticed data change, and it is
required.

**One command writes both `measured.*` files.** The `.md` is required, not optional: with no
enforcement layer, the readable table is the only way anyone checks a claim without running
the harness. Generating the pair separately is how they drift.

### 4. `validation/README.md` — the template's real payload

Since the tier ships as convention rather than machinery, this file *is* the convention. The
template carries five sections:

1. **What this folder is** — evidence of measured behaviour, committed deliberately;
   superseded by regeneration, never edited by hand.
2. **The two authority rules**, verbatim as above.
3. **The index** — one row per corpus:

   | Corpus | What is measured | Gate | Regenerate with |
   |---|---|---|---|
   | `<corpus>` | one line | which check reads `expected.json` | the exact command |

4. **How to add a corpus** — make the directory, write `expected.json` with a justification
   comment per threshold, run the harness to produce `measured.*`, add the index row, point
   the gate at `expected.json`.
5. **What does not go here** — the scope boundary below, including that ground-truth *labels*
   are input data, not evidence: they come with the corpus and stay out of this tree.

The *how the harness works* write-up stays in `docs/`. The tier holds evidence and points at
the prose, exactly as `work/` points at ADRs rather than restating them.

### 5. Where it sits against the other tiers

New row for the blueprint's provenance table:

| The question | Lives in | Shape |
|---|---|---|
| How well does it actually perform, and measured against what? | `validation/<corpus>/` | hand-edited `expected.json` + regenerated `measured.json`/`.md` |

Boundaries: `docs/` keeps the harness runbook; `tests/`/CI keeps the gate itself;
`validation/` holds only what the gate reads and what a human reads to check the claim.
When a measured number moves and the threshold is deliberately relaxed, the `expected.json`
diff *is* the record — unless the relaxation is direction-setting (accepting worse accuracy to
buy something else), which is an ADR like any other trade-off.

### 6. Why `validation/` and not `qa/`

`qa/` is the honest, unloaded word. `validation/` is the regulated one: IEC 62304 / ISO 13485
expect *requirement → verification protocol → verification record*, and this tree is already
shaped like the third. The name costs nothing now and saves a rename if a safety-case question
ever resolves toward "this software is an owned control."

**Stated plainly in the ADR:** naming a directory `validation/` makes no compliance claim. It
declines to fight the vocabulary later; it does not assert a process.

### 7. Size

No hard ceiling. The rule is behavioural: `measured.json` must stay reviewable **as a diff**.
Past that point the record holds aggregate statistics and the harness regenerates per-record
detail on demand — the evidence claim survives, the git blob does not grow unbounded.

### Scope boundary — what this tier does *not* hold

Ground-truth accuracy evidence only. Explicitly excluded, with where they go instead:

- **Golden-output snapshots** → `tests/`. Established home beside their consumer, no audience
  beyond the test runner. Nobody audits them to check a claim.
- **Ground-truth labels themselves** → wherever the corpus lives. They are input data, not
  evidence of behaviour, and they are usually externally sourced and large.
- **Performance / latency benchmarks** → nowhere yet. Environment-dependent, so a committed
  record is frequently noise rather than evidence. The structure would extend cleanly if a
  repo needs it; do not ship a tier claiming coverage it has not earned.
- **External reports and scan baselines** → out. Different provenance model entirely: produced
  outside the repo and not regenerable from it, so §2 and §3 cannot apply.

### Implementation path (on acceptance)

1. **ADR-0009** — the missing category, the expected/measured split framed as legibility
   rather than prevention, fixed generic filenames, the naming rationale plus its non-claim,
   the scope boundary, and **deferred enforcement with its trigger** (below).
2. **Blueprint** — an "Opt-in — validation evidence" bullet beside the external-tracker one,
   the layout entry, and the provenance-table row.
3. **`templates/validation/`** — `README.md` per §4 and one example corpus directory with all
   three files and a filled provenance block. Generic per the templates rule: no real corpus,
   no real numbers presented as defaults.
4. **`just sync-plugin` + `just validate`**, CHANGELOG entry, `plugin.json` version bump —
   this changes what a consumer receives.
5. **AGENTS.md** index line.
6. **The originating repo adopts at its one existing corpus**, without waiting for the plugin
   round trip. The valuable and irreversible-in-cost part is the **enforced-versus-recorded
   judgement** — which numbers the gate fails on, versus which are recorded for a reader. One
   file has done both jobs so far, so the question has never been asked; asking it once, at
   one corpus, is cheap, while asking it retroactively across three is three separate
   after-the-fact judgements. The mechanical remainder is a rename, a `.md` companion off the
   same command, a provenance block in the writer, and pointing the gate at `expected.json`.
   `corpus_digest` is deferred there per §3 — that corpus has a stable published version
   string, so the digest would be guarding only against local corruption.

This repo will never carry a `validation/` tier itself — it ships no measurable behaviour. The
template is the only artifact here, the usual state for the opt-in tiers.

### Deferred, with a trigger — enforcement

No CI check and no `CODEOWNERS` requirement ship with this. CI complexity is not wanted during
development, and `CODEOWNERS` is overhead in a solo repo by the blueprint's own reckoning.
Recorded in the ADR's Consequences, in the idiom ADR-0007 and ADR-0008 already use, so it is
carried at zero cost rather than lost:

> Enforcement of the two authority rules is deferred. It becomes worth adding when either
> trigger fires: **a second person commits to `validation/`**, or **a threshold moves without
> a justification comment beside it**. The two candidate mechanisms are a `CODEOWNERS` entry
> on `validation/*/expected.json` (targets the goalpost move, which is the common case) and a
> check that flags a `measured.*` diff whose `provenance.commit` did not change (targets a
> hand-edited record, which is rarer). Neither is needed for a solo repo in active
> development.

Deliberately **not** opened as a `work/` item: an item nobody is working cannot satisfy
`work/`'s exit rule, so it would sit in the tree as precisely the stale artifact that rule
exists to prevent.

## Open questions

None outstanding. Enforcement is deferred rather than open — it has a decision and two
triggers, above.

The one thing that stays genuinely unproven until the originating repo adopts: whether the
enforced-versus-recorded line is obvious in practice, or whether most repos will find that
nearly every measured number wants to be enforced — in which case `expected.json` stops being
small and §2's justification-per-threshold discipline gets expensive. That is what first
adoption tests.

## Alternatives

- **`tests/baselines/`** — the standard golden-file convention, cheapest, no new top-level
  directory, lives beside its consumer. Rejected because it buries validation evidence inside
  the test tree, where a collaborator auditing an accuracy claim will not look, and because
  the human-readable table is a document rather than a fixture.
- **`docs/validation/`** — has precedent (a generated, test-gated reference already lives under
  `docs/` in the originating repo). Rejected: `docs/` is prose canon, and a machine-read gate
  input sits oddly in it. Keeps the runbook, loses the evidence.
- **`reports/` at root** — the usual name for generated output, and exactly the problem: it
  reads as gitignorable scratch, while these files are committed deliberately.
- **`work/`** — rejected on the exit rule. See *Motivation*.
- **`qa/`** — see §6. A live option if the regulated vocabulary is judged misleading.
- **Repo-specific record names** (`beat_truth.json` and friends) — rejected in §2: they carry
  no signal about authority versus record, and the tier's whole value is that a stranger can
  tell the difference at a glance.
- **TOML for `expected.*`.** Chosen first, then reversed — see the note in §2. Its only
  advantage here is comment syntax, and a required `why` field delivers the same adjacency with
  better tooling behaviour and no dependency. Its cost is paid by every non-Python gate, and
  under this project's dependency rule that cost is an interruption rather than an install.
- **One file, gate reads the record directly** — simplest, no duplication. Rejected: every
  regeneration becomes a potential silent goalpost move, and making that visible is the tier's
  main job.
- **Do nothing; decide per repo.** Reasonable while there is one file. Rejected because the
  originating repo is already at three corpora and rising, and because the expected/measured
  rule is the kind of thing every repo would otherwise re-derive — badly, and only after being
  bitten.
